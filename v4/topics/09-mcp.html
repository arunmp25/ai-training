MCP: USB-C for AI

The Model Context Protocol is an open standard for plugging AI apps into tools and data. Build a connector once, and any MCP-compatible AI app can use it. Remember the drawer of old phone chargers? This is the USB-C moment.

⏱ 30 sec

🎤 Say MCP is like USB-C for AI: one standard plug between AI apps and tools or data. Build the connector once and any compatible app can use it.

  • Introduced by Anthropic in late 2024 as an open standard, and now supported across many AI apps and vendors.
  • Analogy: before USB, every device had its own plug.

Compare

A regular tool call vs an MCP tool

To the model they look exactly the same. What changes is where the tool lives and how your app finds and runs it.

⏱ 3 min

🎤 Say A common question: is an MCP tool different from the tool calls we saw in Topic 12? For the model, no. It still gets a tool list, replies with tool_use and receives a tool_result. MCP changes the plumbing on our side: the tool is described and run by a separate server, and the app discovers it instead of hard-coding it.

  • Start on “Side by side”, then switch to “On the wire” and point out that steps 2 and 4 are identical in both columns.
  • The prefix mcp__rating__ is how Claude Code names MCP tools, so tools from different servers never clash.
  • Rule of thumb: one app and a few tools you own, a regular tool call is fine. Many apps, or tools supplied by a vendor, use MCP.
Compare

API vs MCP: MCP does not replace your APIs, it wraps them

An API is for programs your developers write in advance. MCP is for AI apps that decide at run time which tool to call.

⏱ 3 min

🎤 Say MCP is not a replacement for APIs. Your rating engine keeps its API. An MCP server is a thin adapter in front of it that describes the useful actions in a way an AI app can discover and call.

  • “Side by side”: the key rows are “who calls it” and “contract”. Every API is different; every MCP server speaks the same protocol.
  • “MCP wraps your API”: about ten lines of Python using the official MCP SDK. The docstring becomes the tool description the model reads.
  • “Why not just REST?”: a fair question from developers. It works for one app; it stops scaling with many apps, many systems and many endpoints.

In practice

Local and remote servers

💻 Local server

Runs on your own machine, started by the AI app. Good for files, local databases and developer tools.

{
  "mcpServers": {
    "docs": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "./docs"]
    }
  }
}

Example config file (e.g. .mcp.json in a project for Claude Code)

☁️ Remote server

Hosted at a URL, usually with a login (OAuth). Good for SaaS tools like ticketing, CRM, docs and chat. Often offered as “connectors” in AI apps.

{
  "mcpServers": {
    "tickets": {
      "type": "http",
      "url": "https://mcp.example.com/tickets"
    }
  }
}

Illustrative URL. Use the one your vendor provides.

Takeaways

What to remember

🔌 One standard plug

Build a connector (MCP server) once; every MCP-compatible AI app can use it.

🧩 Host · client · server

The AI app hosts, the server exposes tools, resources and prompts from a system.

🔐 Trust carefully

Only use servers you trust, with the least access they need.
