🎤 Say Here are the exact messages. The model stops with tool_use, the app runs the tool and sends back the result with the same id, and the whole conversation is re-sent each time.

  • Key details: the model ends its turn with stop_reason: "tool_use", meaning “I’m waiting for a result”. Each call has an id, and the result must quote the same id.

Many tools at once

Parallel or one after another?

If calls don’t depend on each other, the model can ask for several in one turn. If one needs another’s result, they must run in sequence. Pick a request.

⏱ 2 min

🎤 Say Independent calls can be requested together in one turn. If one call needs another’s result, they have to run one after another.

  • Parallel calls save round trips, which means less waiting and fewer tokens re-sent.
  • The harness decides whether to actually run them in parallel. Writes are often run one at a time on purpose.
Steering

Your app can tell the model how to use tools on each request. Request: “Hi! What can you help me with?” with the tool get_claim_status available.

⏱ 2 min

🎤 Say Tool choice controls whether the model may, must or must not use tools on a request. Auto is right most of the time.

  • auto is the default and right most of the time.
  • Forcing a specific tool is a neat trick for structured output: force record_invoice and you always get JSON in that shape (two slides on).
Errors

When a tool fails, the error message is a prompt

The customer typed their claim number as “45-12”. The tool call fails. Compare what the model can do with each error message.

⏱ 2 min

🎤 Say When a tool fails, the error message is a prompt. A clear error lets the model fix its own input or ask the user.

  • Return errors to the model (marked as an error) instead of crashing. A clear message lets it fix its own input or ask the user.
  • Also: set timeouts, cap retries, and never put secrets or stack traces in error text.

🎤 Say Need clean data instead of prose? Define a tool whose schema is the shape you want. The model fills it in like a form.

Designing tools a model can use well

  
Tools are a user interface for the model. Flip each card.

  

  
⏱ 3 min
🎤 Say Tools are a user interface for the model. Design them around tasks, not around every API endpoint.
  • The biggest anti-pattern: wrapping every API endpoint as a tool. Design around tasks the model needs to do, not around your API.
  • Return what helps the next step: names and IDs, not 5 MB of raw JSON.

Takeaways

  
What to remember

  

    
📜 Name + description + schema
That’s all the model knows about a tool. Write it like a prompt; use enums and required fields as guard rails.

    
🔁 Request → result, by id
The model stops with a tool_use; your app runs it and returns a tool_result with the same id. Repeat until done.

    
🧰 Few, task-shaped tools
Clear errors, concise results, and only the tools the task needs.
